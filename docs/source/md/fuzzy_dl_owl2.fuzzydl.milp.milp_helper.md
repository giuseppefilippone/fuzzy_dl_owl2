# Summary

A Mixed-Integer Linear Programming (MILP) manager for a fuzzy description-logic reasoner that translates fuzzy concepts, roles, and assertions into decision variables and linear constraints, then dispatches the resulting optimization problem to pluggable solver backends such as Gurobi, Python-MIP, and PuLP.

## Description

*MILPHelper* is the optimization core of a fuzzy description-logic reasoner: every fuzzy concept or role assertion about an individual is mapped to a decision variable — by default semi-continuous in [0, 1], representing its degree of truth — and logical axioms, restrictions, and cardinality requirements are compiled into linear inequalities over those variables. Variables are created lazily and cached under canonical names such as "ind:Concept" or "(a,b):role", so repeated lookups for the same assertion always reuse the same variable, and a family of overloaded retrieval entry points accepts strings, individuals, concepts, relations, restrictions, and created individuals, normalising them all into this naming scheme. Crisp concepts and roles are tracked in dedicated sets so their variables can be forced to binary, while nominal (singleton) concepts receive special binary variables together with partition equations enforcing the law of excluded middle, and negated nominals are linked to their positive counterparts through complementary constraints.

Constraints flow through another overloaded dispatcher that accepts expressions paired with an inequality type, a degree, or a numeric right-hand side, normalising everything into a uniform list of inequations. Beyond plain constraints, the helper embeds reusable MILP idioms required by the reasoner: a sorting-network encoding that produces variables holding a non-increasing permutation of an input list (needed for qualified cardinality reasoning), equality constraints for merging individuals, and Big-M style relaxations that tie renamed variables together when nominals are unified. String-valued features are supported by mapping strings to integer codes and back again, and cardinality-restriction objects can be registered for later processing.

Solving is deliberately backend-agnostic: a single dispatch method inspects the configured provider and delegates to dedicated routines for Gurobi, Python-MIP with CBC, or PuLP with CBC, GLPK, HiGHS, or CPLEX. Each backend builds the model, filters out duplicate and vacuous constraints, applies tight feasibility tolerances, solves, and packages the outcome into a solution object that distinguishes an optimal objective value from an inconsistent knowledge base. Solver libraries are imported lazily inside the solving routines so only the chosen backend needs to be installed, and where a backend lacks native semi-continuous variables (GLPK and CPLEX through PuLP), auxiliary binary variables and bounding constraints emulate them; a companion routine also locates the CPLEX command-line binary across macOS, Linux, and Windows by searching the PATH, well-known environment variables, and standard installation directories.

An optional partitioning strategy exploits the fact that fuzzy reasoning queries often yield weakly coupled problems: a graph is built in which variables are connected whenever they co-occur in a constraint, breadth-first search splits it into connected components, and each component containing objective variables is then solved as an independent, much smaller MILP, with any infeasible sub-problem declaring the whole knowledge base inconsistent. Diagnostics are first-class: the helper tracks which variables should be displayed, prints their optimal values, reports the membership degrees of numeric feature values against their linguistic labels, and writes model and solution files to a results directory for later inspection. A deep-copy cloning facility lets the reasoner explore alternative scenarios without mutating the shared problem state.
